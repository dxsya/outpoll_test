# План реализации Dashboard торгового оборота

## 1. Выбранный стек

- **Next.js 16+ с App Router** — основа приложения, маршрутизация и запуск production-сборки.
- **TypeScript** — строгая типизация API-ответов, нормализованных данных, фильтров и состояния.
- **React 19** — UI-компоненты и интерактивность.
- **TanStack React Query** — запросы к публичным API, кэширование, дедупликация одинаковых запросов, отмена устаревших запросов, retry и состояния загрузки/ошибки.
- **Zustand** — клиентское состояние интерфейса: выбранный диапазон, категории, видимость серий и состояние отображения графика.
- **nuqs или собственный адаптер search params** — двусторонняя синхронизация фильтров и диапазона с URL. URL является сериализованным представлением состояния, а Zustand хранит рабочее состояние интерфейса.
- **Apache ECharts через `echarts-for-react`** — основной график. ECharts предоставляет масштабирование, crosshair, tooltip, legend и адаптивный Canvas/SVG-рендеринг; форматирование и мобильное поведение будут настроены вручную.
- **Tailwind CSS** — адаптивная раскладка и состояния компонентов.
- **Vitest + Testing Library** — unit- и component-тесты.
- **Playwright** — smoke-тесты пользовательских сценариев в браузере.
- **ESLint + Prettier** — единый стиль и раннее обнаружение ошибок.

## 3. Источники и получение данных

### Kalshi

Использовать публичный API Kalshi для получения списка рынков и исторических данных по объёму. Реализация должна учитывать пагинацию, лимиты API и возможные CORS-ограничения. Если браузерный запрос к конкретному endpoint заблокирован политикой CORS, нужно выбрать другой публичный endpoint той же платформы, а не подменять данные моками.

### Polymarket

Использовать публичные Gamma/CLOB API Polymarket для списка рынков, категорий и доступных исторических объёмов. Контракт API нужно проверить на реальных ответах перед написанием адаптера, потому что поля и шаг исторических данных могут отличаться от Kalshi.

### Общий адаптер

Каждая платформа получает собственный API-модуль, но наружу отдаёт одинаковую доменную модель:

```ts
type Platform = "kalshi" | "polymarket";

type MarketCategory = {
  id: string;
  label: string;
};

type MarketVolumePoint = {
  timestamp: string;
  volumeUsd: number;
  marketId: string;
  categoryId: string;
  platform: Platform;
};
```

Адаптер отвечает за преобразование валютных значений в USD, нормализацию timestamp, категорию без значения (`Uncategorized`), обработку pagination и валидацию ответа. Для валидации внешних данных использовать Zod или эквивалентный schema-parser. Компоненты UI не должны знать о различиях API платформ.

Запросы выполняются из клиентского слоя через React Query. `queryKey` должен включать платформы, диапазон, категории и версию формата данных, например:

```ts
["volume-dashboard", { range, categories: sortedCategoryIds }];
```

React Query будет:

- возвращать кэшированный результат для уже загруженного набора параметров;
- дедуплицировать параллельные запросы с одинаковым `queryKey`;
- передавать `AbortSignal` в `fetch`, чтобы отменять устаревший запрос;
- сохранять предыдущие данные через `placeholderData`, чтобы график не исчезал при смене диапазона;
- повторять временные ошибки ограниченное число раз и не повторять ошибки валидации ответа;
- показывать пользователю дату последнего обновления данных.

## 4. Модель данных и расчёт volume

1. Получить список доступных рынков обеих платформ.
2. Отфильтровать рынки по выбранным категориям.
3. Получить исторические данные для оставшихся рынков в выбранном диапазоне.
4. Привести timestamps к UTC и сгруппировать точки по календарному дню.
5. Суммировать `volumeUsd` всех выбранных рынков внутри дня отдельно для Kalshi и Polymarket.
6. Объединить две платформы по общей временной шкале, заполняя отсутствующие значения `null`, а не нулём. Это позволит отличать отсутствие данных от реального нулевого оборота.
7. Для диапазона «всё время» выбрать подходящий bucket автоматически: день для коротких периодов, неделя или месяц для длинной истории.
8. При большом числе точек использовать агрегацию на уровне запроса или downsampling перед передачей данных в ECharts. Нельзя строить график из каждой сырой сделки.

Нужно явно зафиксировать в README, что именно API считает volume: количество контрактов, номинальный USD-оборот или сумму сделок. Если определения платформ различаются, показать это в подсказке интерфейса и не выдавать показатели за полностью сопоставимые без оговорки.

## 5. Состояние и URL

В Zustand хранить:

- `range`: `7d | 30d | 90d | all`;
- `selectedCategoryIds: string[]`;
- `hiddenPlatforms: Platform[]`;
- локальное состояние открытого tooltip/выбранной точки, если оно нужно графику.

В URL синхронизировать как минимум `range` и `categories`. Пример:

```text
/?range=30d&categories=politics,sports
```

Правила синхронизации:

- при первом открытии URL валидируется и становится начальным состоянием;
- изменение фильтра создаёт новую history entry только для пользовательского действия;
- восстановление состояния через Back/Forward не создаёт циклическую запись в history;
- порядок категорий сериализуется стабильно;
- неизвестные категории и некорректный диапазон игнорируются с безопасным fallback;
- состояние «все категории» кодируется отдельно от состояния «категории сняты», чтобы эти сценарии нельзя было перепутать.

## 6. Компоненты и поведение интерфейса

### Dashboard shell

Отвечает за загрузку данных, композицию панели фильтров, графика, summary-метрик и состояний loading/error/empty. Данные и преобразования передаются вниз, чтобы график оставался презентационным компонентом.

### Панель управления

- segmented control для диапазона `7д / 30д / 90д / всё время`;
- список категорий с checkbox и количеством доступных рынков;
- кнопки «Выбрать все» и «Сбросить»;
- легенда платформ с возможностью скрыть серию;
- кнопка повторной загрузки при ошибке.

### График

- две серии на одной временной оси;
- USD-форматирование оси Y (`$1.2M`, `$340K`, `$850`);
- локализованное форматирование дат на оси X;
- tooltip с обеими платформами для ближайшей даты;
- crosshair и выделение ближайшей точки;
- клик по легенде скрывает или возвращает серию;
- на touch-устройствах tooltip открывается по тапу и перемещается drag-жестом;
- изменение диапазона и фильтров сопровождается плавным обновлением серии без очистки старого графика;
- resize observer и корректное поведение на ширине от 360 px.

### Состояния

- skeleton повторяет геометрию будущих фильтров, summary и графика;
- ошибка содержит понятное описание, кнопку Retry и сохраняет предыдущий успешный график, если он есть;
- пустой результат при снятых категориях объясняет, что нужно выбрать хотя бы одну категорию;
- состояние «нет данных за период» появляется только когда категории выбраны, запрос успешен, но точек в диапазоне нет;
- состояние устаревших данных явно помечается, если выполняется фоновое обновление.

## 7. Доступность и адаптивность

- все интерактивные элементы доступны с клавиатуры;
- видимый `:focus-visible` с достаточным контрастом;
- у переключателей платформ и категорий корректные `aria-label`, `aria-pressed` или `aria-checked`;
- график имеет текстовое summary и таблицу/сводку данных для screen reader;
- цвет не является единственным способом различить платформы: добавить разные штрихи/маркеры и подписи;
- минимальная ширина 360 px, горизонтальный overflow страницы запрещён;
- touch target контролов не меньше 44 px;
- tooltip не должен выходить за границы viewport.

## 8. Производительность

- не вычислять агрегаты на каждый render: мемоизировать только дорогие производные данные и измерить их стоимость;
- сортировать category ids перед формированием `queryKey`;
- ограничить число одновременно запрашиваемых страниц и использовать `Promise.allSettled` для независимых платформ;
- применять `staleTime` для данных, которые не должны запрашиваться повторно при каждом переключении вкладки;
- использовать `placeholderData` и фоновое обновление вместо размонтирования графика;
- агрегировать точки до передачи в ECharts;
- при десятикратном росте данных проверить память, время нормализации и число SVG/Canvas-элементов.

## 9. План разработки по этапам

### Этап 1. Инициализация

- создать Next.js-проект с TypeScript и App Router;
- установить React Query, Zustand, ECharts, Tailwind, Zod и тестовые инструменты;
- настроить ESLint, Prettier и базовый `QueryClientProvider`;
- добавить `.env.example` только для необязательных публичных настроек API.

### Этап 2. Интеграция данных

- исследовать реальные публичные endpoints обеих платформ;
- зафиксировать пример ответа и ограничения API в README;
- написать Zod-схемы и адаптеры Kalshi/Polymarket;
- покрыть нормализацию, pagination, категории, timestamp и ошибки тестами.

### Этап 3. Доменная агрегация

- реализовать фильтрацию по категориям;
- реализовать дневную/недельную/месячную агрегацию;
- объединить временные ряды платформ;
- добавить тесты на пустые значения, дубликаты, UTC и длинные диапазоны.

### Этап 4. Состояние и URL

- создать Zustand store с actions и безопасными initial values;
- добавить парсер и сериализатор URL;
- проверить прямое открытие ссылки, Back/Forward и перезагрузку страницы.

### Этап 5. UI и график

- собрать responsive dashboard;
- добавить skeleton, error, retry и два разных empty state;
- настроить ECharts, legend, tooltip, crosshair и mobile pointer events;
- добавить доступные подписи и keyboard navigation.

### Этап 6. Дополнительные функции

- summary: общий оборот, изменение к предыдущему периоду и доля платформ;
- экспорт агрегированных данных в CSV;
- системная светлая/тёмная тема;
- выделение аномальных пиков только после базовой стабилизации графика.

### Этап 7. Проверка и публикация

- выполнить lint, typecheck, unit-тесты и production build;
- проверить сценарии Playwright на desktop и ширине 360 px;
- проверить реальные запросы без mock server;
- проверить отмену запроса при быстром переключении диапазонов;
- проверить доступность с клавиатуры и видимый focus;
- запустить демо на localhost и описать команду запуска в README.

## 10. Критерии готовности

- `npm run dev` запускает dashboard на localhost;
- на одном графике отображаются реальные данные Kalshi и Polymarket;
- диапазон, категории и видимость платформ работают независимо и синхронизируются с URL;
- Back/Forward восстанавливают ожидаемое состояние;
- запросы кэшируются, дедуплицируются и отменяются при смене параметров;
- старые данные остаются видимыми во время загрузки нового набора;
- реализованы loading, error, retry, empty и no-data-for-period состояния;
- tooltip, crosshair, legend и touch-взаимодействия работают;
- интерфейс доступен с клавиатуры и не ломается на 360 px;
- проверены производительность и поведение при большом количестве точек;
- в README объяснены источники данных, формула volume, ограничения сравнения платформ и архитектурные решения.
